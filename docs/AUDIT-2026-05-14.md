### F6 [HIGH] `pyperclip.paste()` / `pyperclip.copy()` in hotkey handler are not wrapped — locked clipboard crashes the listener thread
- **File:** `clipboard_hotkey.py:198, 222`
- **What:** `handle_hotkey()` is invoked from the `pynput` keyboard listener thread on every hotkey press. Its very first action (line 198) is `text = pyperclip.paste()`, followed later by `pyperclip.copy(converted_mac)` at line 222. Neither call is inside a `try`/`except`. On Windows, `pyperclip` raises `pyperclip.PyperclipWindowsException` (wrapping `ctypes.WinError`) when `OpenClipboard()` returns 0 — which happens routinely whenever another process holds the clipboard: snipping/screenshot tools, RDP/VNC clipboard sync, Office save dialogs, browser drag-drop, and PowerToys' clipboard history all hold the clipboard for tens to hundreds of milliseconds at a time. When the user happens to press the hotkey during that window, the exception propagates out of `handle_hotkey` into the pynput listener thread.
- **Why it's a bug:** pynput's internal `Listener._run` catches the exception and stops the listener (it calls `self._handler` with `KeyCode`/`Key.error` then exits). The thread dies, `listener.stop()` is never called from user code, and the hotkey is **silently dead until the app is restarted**. The user sees no error popup (because `show_error_popup` is never reached), the tray icon stays green, and pressing the hotkey simply does nothing — a high-impact, hard-to-diagnose failure mode that triggers under perfectly normal Windows usage.
- **Proposed fix:** Wrap both calls in `try`/`except` and surface the error through `format_popup_request_queue` so the user sees feedback:
  ```python
  try:
      text = pyperclip.paste()
  except pyperclip.PyperclipException as e:
      format_popup_request_queue.put({'type': 'error',
          'message': 'Clipboard busy, try again', 'duration': settings.get('notification_duration', 3)})
      return
  ```
  Same wrapper around line 222's `pyperclip.copy()`. Additionally consider a brief `time.sleep(0.05)` + one retry, since contention is usually transient.
- **Effort:** S

### F11 [HIGH] Closing OUIDownloadDialog mid-download orphans the worker thread; re-opening spawns a concurrent worker that races on `oui.csv.tmp` and the shared progress queue
- **File:** `clipboard_hotkey.py:685-731, 778-781` (`OUIDownloadDialog._start_download` / `closeEvent`) with `oui_lookup.py:97-104` (temp-file write path)
- **What:** `_start_download` spawns `t = threading.Thread(target=worker, daemon=True)` (line 730) and keeps no reference to it on `self`. `closeEvent` only stops `_poll_timer` (line 779-780); it does not signal the worker to cancel, does not `join()`, and does not drain `oui_download_progress_queue`. Concretely, after the user dismisses the dialog while the ~3.5 MB IEEE download is still in flight: (1) the worker thread continues to run, calling `oui_db.download(progress_callback=progress_cb)` (line 705), which keeps `response.read(chunk_size)`-ing into `data` and pushing `{'status': 'downloading', ...}` messages into `oui_download_progress_queue` — a module-level **unbounded** `queue.Queue()` (line 113) with no reader; messages accumulate until the worker eventually finishes and pushes its final `'done'` / `'error'` message. (2) The worker reaches `os.remove(self.oui_path)` + `os.rename(temp_path, self.oui_path)` (`oui_lookup.py:102-104`) and silently overwrites the user's OUI database with no UI consent, **after** the user closed the dialog presumably to cancel. (3) If the user clicks "Update OUI database" again from the Settings dialog (line 1042: `OUIDownloadDialog(self).exec_()`), a second `OUIDownloadDialog` is constructed; its `__init__` immediately calls `_start_download` → a **second** worker thread starts. Both workers now race: each writes to the same `temp_path = self.oui_path + ".tmp"` (`oui_lookup.py:98`), opens it `with open(temp_path, 'wb')` (truncating whatever the other wrote), and races on the `os.remove(oui_path); os.rename(temp_path, oui_path)` pair. Outcomes range from interleaved `.tmp` writes (garbled OUI database — fails F3 size/structure checks if those were added) to `WinError 32` on `os.rename` when one worker has the temp file still open (file destroyed per F2, replacement fails). (4) The new dialog's `_poll_progress` reads from the same queue and **immediately consumes the previous worker's accumulated stale messages** — including any stale `'done'` or `'error'` that the previous worker has already pushed. The new dialog will then close itself prematurely with the prior worker's outcome, while the new worker is still downloading. (5) On `app.quit()` the daemon thread is killed mid-write — if it was inside the `os.rename` call, F2 already documents that gap; if it was inside `with open(temp_path, 'wb') as f: f.write(data)`, the temp file is left partial (next launch with a future "resume from .tmp" feature would be wrong).
- **Why it's a bug:** Several user-visible failure modes from a routine "close and retry" workflow on a flaky network — none of them ever surface an error to the user, because the orphaned worker's `'error'` message goes into a queue nobody reads, and the new worker's outcome may be masked by the previous worker's stale message. The damage compounds with F2 (non-atomic replace) and F3 (no content validation): two workers racing on the temp file can produce a corrupted CSV that F3 would otherwise reject, but here both workers' `data` buffers pass the `len(data) >= 1000` check independently. Severity is **High** because (a) the cancel path silently does nothing — there is no cancel — and the user's mental model says "I closed the dialog, the download stopped"; (b) the race is reachable through normal use ("dialog hung, close it, try again") on any user with a slow connection; (c) it can corrupt the OUI database; (d) it cannot be diagnosed from the UI.
- **Proposed fix:** Four layers, in priority order. (1) Store the worker thread on `self`: `self._worker_thread = threading.Thread(target=worker, daemon=True); self._worker_thread.start()`. Add a `threading.Event` `self._cancel_event` that `worker` checks between chunks (and that `download()` consults via a `cancel_event` parameter), so close-while-downloading actually stops the read loop. (2) In `closeEvent`, drain `oui_download_progress_queue` (`while True: try: oui_download_progress_queue.get_nowait() except queue.Empty: break`) so stale messages don't bleed into the next dialog. (3) Gate `manual_oui_update` (clipboard_hotkey.py:1040) on a module-level "download in progress" flag (`_oui_download_in_progress: bool` guarded by a `threading.Lock`) — set on worker start, cleared on worker exit — and show "Download already in progress" if the flag is set, preventing a second worker from being spawned at all. (4) Replace the module-level `oui_download_progress_queue` with a per-dialog `queue.Queue()` instance attached to the dialog (`self._progress_queue = queue.Queue()`) and passed into the worker closure; this structurally prevents cross-instance message leakage even if (2) is missed in some future refactor. F2's `os.replace` fix is also a prerequisite for (1)+(3) to be safe under cancel.
- **Effort:** M

### F13 [HIGH] "Start with Windows" checkbox is non-functional — value is persisted but never applied to the Windows registry
- **File:** `clipboard_hotkey.py:932-935, 1032, 1551` (settings dialog + default) — and the *absence* of any registry-write code anywhere in the repo
- **What:** The Startup Options group in `SettingsDialog.__init__` (lines 929-937) constructs a `QCheckBox("Start with Windows")` and binds it to `settings.get('autostart', False)`. `save_settings()` on the dialog (line 1032: `settings['autostart'] = self.autostart_checkbox.isChecked()`) writes the boolean back into `settings.json`. **That is the entire end-to-end implementation.** Grep-confirmed: there is no `import winreg`, no `winreg.OpenKey`, no `SetValueEx`, no `DeleteValue`, no reference to `Software\Microsoft\Windows\CurrentVersion\Run` anywhere in `clipboard_hotkey.py` or any other source file. `settings.get('autostart', ...)` is only read by `SettingsDialog.__init__` (line 933) to populate the checkbox state — nothing in `main()` (line 1591) or `listen_hotkey` or the tray-icon setup ever consults `settings['autostart']` and acts on it. The user can check the box, click Save, see "saved" — and the app does not register itself for autostart in any way.
- **Why it's a bug:** This is a silent feature failure on a user-advertised setting (`README.md:23` and `README.md:55` both promote the autostart capability; `DEVELOPMENT_LOG.md:125` claims "Implemented autostart logic: add/remove from Windows startup based on user preference" — that claim does not match the code). The user enables the setting, restarts the machine, the app does not start, and there is no error surfaced because no code path exists to fail. Severity High because the feature is documented as working in the README and the user has no way to discover it does not. Note: the **installer** (`installer.iss:51`) does write a Start-Menu Startup-folder shortcut for users who tick the installer's "auto-start" option, so installer-driven users *appear* to get autostart for free — masking the fact that toggling the in-app setting after install does nothing. The installer-side entry is in `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`, not the registry, so the two surfaces would also be mismatched if the registry write were ever implemented (toggling "off" in-app would not remove the installer shortcut). Task 9 will catalogue the installer half; this finding documents the in-app half.
- **Proposed fix:** Implement the missing handler. Add a helper at module scope:
  ```python
  import winreg
  AUTOSTART_KEY = r"Software\Microsoft\Windows\CurrentVersion\Run"
  AUTOSTART_VALUE = "MAC Converter"

  def apply_autostart(enabled: bool) -> None:
      try:
          with winreg.OpenKey(winreg.HKEY_CURRENT_USER, AUTOSTART_KEY, 0, winreg.KEY_SET_VALUE) as k:
              if enabled:
                  exe = sys.executable
                  # Quote the path in case it lives under "C:\Program Files\..."
                  cmd = f'"{exe}"' if " " in exe else exe
                  winreg.SetValueEx(k, AUTOSTART_VALUE, 0, winreg.REG_SZ, cmd)
              else:
                  try:
                      winreg.DeleteValue(k, AUTOSTART_VALUE)
                  except FileNotFoundError:
                      pass  # already absent — fine
      except (OSError, PermissionError) as e:
          print(f"[WARNING] autostart toggle failed: {e}")
  ```
  Call `apply_autostart(settings['autostart'])` once at the end of `SettingsDialog.save_settings` (after `save_settings(settings)`), and also call it once at app startup so that an externally-edited `settings.json` is reconciled. Also: detect frozen-vs-source mode (`getattr(sys, 'frozen', False)`) — when running from source, `sys.executable` is `python.exe` and registering that would launch a bare Python REPL on login; either skip the registry write or fall back to `"<python> <script_path>"`. Finally: document the interaction with `installer.iss:51` (Task 9) — pick one mechanism, not both.
- **Effort:** M

### F14 [HIGH] Hotkey input has no validation on Save — gibberish persists to disk and is recovered on next launch only because `listen_hotkey` has a fallback
- **File:** `clipboard_hotkey.py:1028-1038` (save handler) and `clipboard_hotkey.py:1527-1533` (listener fallback)
- **What:** `SettingsDialog.save_settings` (line 1028) takes the raw `self.hotkey_input.text().strip()` and stores it in `settings['hotkey']` without parsing, without checking that any modifier is present, without verifying the token is in pynput's vocabulary, and without confirming `keyboard.HotKey.parse(format_hotkey_for_pynput(...))` succeeds. A user can type `xyz+abc`, `m+m+m`, an empty string after stripping, a single non-modifier `m`, or even `';--DROP TABLE`-style input, click Save, and the value goes straight to `settings.json`. The dialog then accepts (`self.accept()`) and closes with no feedback. The good news is that `listen_hotkey` (lines 1527-1533) does wrap the `keyboard.HotKey.parse(formatted)` call in `try/except Exception` and on failure falls back to `<alt>+<shift>+m`, so the app does **launch** even with a broken hotkey — the disaster scenario flagged in the task spec ("app becomes unlaunchable until the user manually edits `settings.json`") is actually averted.
- **Why it's a bug:** Three remaining problems even with the fallback: (1) **No user feedback.** The fallback path only `print()`s to stderr (line 1532) — for a frozen tray app there is no console, so the user sees their custom hotkey "saved successfully" in the Settings dialog, restarts, and the app silently uses the default hotkey forever. They have no idea their input was rejected. (2) **The bad value stays in `settings.json` permanently.** The fallback computes a `parsed_hotkey` for the current session only; nothing rewrites `settings['hotkey']` back to the default, so every launch from now on re-runs the parse failure, re-prints the error to a console nobody sees, and re-falls-back. The Settings dialog on next open re-populates the input with the broken string (line 902), so the user sees their typo persisted and assumes it's working. (3) **Silent acceptance of structurally-bad-but-parseable input.** `format_hotkey_for_pynput` only wraps tokens in the hardcoded `special_keys` set (line 1512-1517) in angle brackets — anything else is passed through as a regular char. So `m+n+o` parses successfully as "press m and n and o simultaneously" (which the user will never trigger), and `xyz` parses as "press the literal three-character key x-y-z" (also impossible). pynput accepts these; they just can never fire. The hotkey effectively does nothing, but no error is raised at parse time, so even the existing print-fallback doesn't catch them. Severity High because the user-visible symptom — "hotkey doesn't work after I changed it in Settings" — is the headline feature of this app, and there is no in-UI signal explaining what went wrong.
- **Proposed fix:** Validate at Save time, surface errors in the dialog, and self-heal `settings.json` on parse failure at startup. Concretely: (1) Add a `validate_hotkey(s: str) -> Optional[str]` helper that returns `None` on success or an error message: requires at least one modifier from `{alt, ctrl, shift, win, cmd}`, requires exactly one non-modifier final token of length 1 (a-z, 0-9) or in a whitelist of named keys (`f1..f12`, `tab`, `enter`, etc.), then attempts `keyboard.HotKey.parse(format_hotkey_for_pynput(s))` and returns its error string if it raises. (2) In `SettingsDialog.save_settings`, call `validate_hotkey` first; on error, show a `QLabel` next to the hotkey input ("Invalid hotkey: <reason>") in red and **do not** call `self.accept()` — keep the dialog open so the user can fix the typo. (3) In `listen_hotkey`'s fallback branch (line 1532), also write the recovered default back to disk: `settings['hotkey'] = 'alt+shift+m'; save_settings(settings)` and surface a one-time error notification through the existing `format_popup_request_queue` so the user sees "Hotkey 'xyz+abc' was invalid, reset to alt+shift+m" the first time they launch after the broken save. F7's atomic-save fix is a prerequisite to make the recovery write safe under concurrent writers.
- **Effort:** M

### F19 [HIGH] FormatSelectorPopup uses a global pynput keyboard listener for Enter — interferes with typing in every other app while the popup is open
- **File:** `clipboard_hotkey.py:1205-1226, 1262-1267`
- **What:** When the format popup opens (and OUI is enabled + loaded + a normalized MAC is in scope), `__init__` calls `self._start_enter_listener()` at line 1210, which constructs a **global** `pynput.keyboard.Listener` (line 1224: `self._enter_listener = keyboard.Listener(on_press=on_press); self._enter_listener.start()`) — not a Qt-scoped `keyPressEvent`, not an `eventFilter` on the popup widget, not a `QShortcut` with `Qt.ApplicationShortcut`. pynput's `keyboard.Listener` hooks the OS-level keyboard input stream (Win32 `SetWindowsHookEx(WH_KEYBOARD_LL)` on Windows), so every Enter keypress *anywhere in the system* — Notepad, browser address bar, password field, Word document, command prompt, another app's dialog — fires `on_press` (line 1214). On the first Enter, `on_press` puts a `{'mac_normalized': ...}` message into `vendor_lookup_request_queue` (line 1218) and returns `False`, which stops the listener (line 1221's `return False` is pynput's documented "stop me" signal). The listener is not constructed with `suppress=True`, so the Enter keypress is **not** swallowed — it still reaches whichever window has focus (the popup itself is a `Qt.Tool` window with `WindowStaysOnTopHint`, which by design does not steal focus, so focus stays in whatever app the user was using). Net effect: the user, mid-sentence in Word with the format popup visible in the corner, presses Enter to add a paragraph break — Word inserts the paragraph break (correct) **and** simultaneously a `VendorPopup` appears (unexpected, possibly covering content). The popup is non-modal and steals no focus, but it's a visible cosmetic shock for any keystroke the user makes anywhere.
- **Why it's a bug:** Three independent harms, all reachable from normal use:
  1. **Surprise UI** — typing Enter in any password field, terminal, or text editor while the format popup is on screen pops a vendor lookup dialog. The user did not opt in to global key capture.
  2. **Privacy-adjacent input observation** — pynput global listeners run for the entire lifetime of the format popup (default `notification_duration` = 3s, configurable up to 10s). During that window, every keypress on the system is delivered to `on_press`, which inspects `key == keyboard.Key.enter`. The implementation only acts on Enter, but the listener *receives* every keystroke — including passwords typed into other apps — because that's how `WH_KEYBOARD_LL` works. The code does not store or log other keys, so there is no actual exfiltration risk, but the architectural choice runs a global keystroke hook for a UI feature that should be a popup-local shortcut, which is the wrong primitive.
  3. **Race with replacement popups** — `show_format_popup` (lines 128-140) closes the previous popup (line 133) and immediately constructs a new one (line 139), which starts a new `_enter_listener`. `pynput.Listener.stop()` is asynchronous — the previous listener's worker thread may not have exited by the time the new listener starts. Two active global Enter listeners means an Enter press fires *both* `on_press` handlers, both put into `vendor_lookup_request_queue`, and the consumer at line 1704 dequeues them one per 50ms QTimer tick, producing two consecutive `show_vendor_popup` calls — the second replaces the first via line 1450-1455, so the user sees a vendor popup that "blinks" or shows wrong-MAC briefly.
- **Proposed fix:** Replace the global listener with a popup-local Qt shortcut. The format popup is a `QDialog`; even though it doesn't take focus by default with `Qt.Tool`, a `QShortcut(QKeySequence(Qt.Key_Return), self, context=Qt.ApplicationShortcut)` bound to a slot that calls `vendor_lookup_request_queue.put({'mac_normalized': self.mac_normalized})` will fire when the popup has focus. To make Enter work *without* clicking the popup first (which is the actual intent — the user just copied a MAC and wants vendor info without leaving their current app), the correct primitive is `keyboard.GlobalHotKeys({'<enter>': callback})` only *briefly* and only if the popup truly needs system-wide capture — but the better UX is to require the popup to be focused (call `self.activateWindow(); self.raise_()` after `show()`, and remove `Qt.Tool` if necessary to allow focus). If global capture truly is required, gate it behind a per-keypress filter that only fires when the focused window is `None` (no foreground app accepting input) or when the popup itself is foreground — using `win32gui.GetForegroundWindow()` cross-checked against the popup's `winId()`. Lastly, when starting a replacement popup (`show_format_popup` line 133-139), explicitly `self._enter_listener.join(timeout=0.1)` on the *previous* popup's listener before constructing the new one to close the two-listener race. F19's severity is **High** because the surprise-popup behavior is reachable on every hotkey trigger and the privacy framing is uncomfortable even though no logging occurs.
- **Effort:** M

### F2 [MEDIUM] Non-atomic replace destroys working OUI database on rename failure
- **File:** `oui_lookup.py:102-104`
- **What:** The download path writes `oui.csv.tmp`, then performs `os.remove(self.oui_path)` followed by `os.rename(temp_path, self.oui_path)`. There is a window between the `remove` and the `rename` where the canonical `oui.csv` does not exist on disk. If `os.rename` then fails — e.g. the file is locked by an AV scanner / Windows Defender mid-write, transient `PERMISSION_DENIED`, disk full at the rename step, the user's antivirus quarantining `.tmp` between write and rename — `os.rename` raises `OSError`, the `except OSError` handler at line 113 reports `"File error: ..."`, and the user is left with **no** OUI database (and an orphaned `oui.csv.tmp`). The next `is_stale` check returns True, but lookups fail until another successful download.
- **Why it's a bug:** Defeats the stated intent ("Atomic write: temp file then rename" — comment on line 97). A successful previous database should not be destroyed by a failed *replacement* attempt. On Windows, the correct atomic replace is `os.replace` (since Python 3.3), which overwrites the destination in a single syscall (uses `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` under the hood) and either succeeds atomically or leaves both files intact.
- **Proposed fix:** Replace lines 102-104 with a single call: `os.replace(temp_path, self.oui_path)`. Remove the prior `os.remove` and `os.path.exists` check. Additionally, add a `finally` (or `except` cleanup) that removes the orphaned `.tmp` file if it exists after a failure, so repeated failed downloads do not leave stale temp files.
- **Effort:** S

### F3 [MEDIUM] 1000-byte size floor lets captive-portal / error HTML pages overwrite the OUI database
- **File:** `oui_lookup.py:94-95`
- **What:** Sanity check `if len(data) < 1000` rejects only obviously-empty responses. The legitimate IEEE `oui.csv` is ~3.5 MB. Captive-portal interception pages, ISP block pages, corporate-proxy error pages, and "this site can't be reached"-style HTML responses are routinely 2-10 KB and will sail past this threshold. The HTML body is then written to disk as `oui.csv`, the previous good database is removed (per F2), and `load()` parses the HTML with `csv.reader`. Because of the `len(row) >= 3` / `len(assignment) == 6` guards, virtually every row is silently skipped, `(True, 0)` is returned, and the database goes "loaded" with zero entries. All vendor lookups silently return `None` for a week (until `update_interval_days` expires).
- **Why it's a bug:** Silent corruption: the user sees the app reporting "OUI database downloaded successfully" (line 107) and then quietly gets blank vendor lookups forever. There is no content-type check (`response.headers.get('Content-Type')`), no magic-byte/structure validation (e.g. that the file begins with the expected header `Registry,Assignment,Organization Name,Organization Address`), and no minimum-entry sanity check in `load()`. The 1000-byte floor is meaningful only against literally-empty responses.
- **Proposed fix:** Layer two cheap defenses: (1) verify `response.headers.get('Content-Type', '').startswith('text/csv')` or at least reject `text/html`; (2) require the first non-blank line of the downloaded bytes to contain the header tokens `Registry` and `Assignment` (case-insensitive substring check is enough). Optionally raise the size floor to a more realistic ~500 KB. If validation fails, do not overwrite the existing database — keep the prior good copy.
- **Effort:** S

### F7 [MEDIUM] `save_settings()` is non-atomic and called from three threads without a lock — settings file can be corrupted to JSON garbage
- **File:** `clipboard_hotkey.py:226, 710, 1037, 1253, 1628` (writers) and `1581-1584` (writer impl)
- **What:** `save_settings()` (line 1581) does `open(path, 'w', encoding='utf-8')` then `json.dump(...)` — Python opens the file in `'w'` mode which **truncates immediately**, then writes JSON incrementally. There is a window during the `json.dump` call where the file on disk is partially written. Three independent threads write to this file with no lock or queue coordination: (a) the pynput listener thread via `handle_hotkey` → line 226 (`save_settings(settings)`) on every hotkey press; (b) the Qt main thread via the Settings dialog at line 1037 and the format selector callback at line 1253; (c) the OUI initialization worker thread at line 1628 after a successful download. If the listener thread truncates the file between the OUI worker's truncate and dump (or any two writers overlap), the resulting `settings.json` is partially-written / not parseable JSON.
- **Why it's a bug:** On the next launch, `load_settings()` at line 1578 catches the resulting `json.JSONDecodeError` with a bare `except Exception` and silently returns `DEFAULT_SETTINGS.copy()` — losing the user's custom hotkey, notification duration, OUI preferences, and last-download timestamp, with no error surfaced. Worse, because the dict written back is the in-memory `settings` which already differs from disk, the user's settings can flip in unexpected ways depending on which writer "won". ### F23 [MEDIUM] `save_settings` writes `settings.json` directly with no atomic boundary — crash or power loss mid-write corrupts the whole settings file

- **File:** `clipboard_hotkey.py:1581-1584`
- **What:** The entire body of `save_settings` is:
  ```python
  def save_settings(settings):
      os.makedirs(SETTINGS_DIR, exist_ok=True)
      with open(SETTINGS_PATH, 'w', encoding='utf-8') as f:
          json.dump(settings, f, indent=2)
  ```
  Opening the canonical `settings.json` with mode `'w'` **truncates the file to zero bytes** before any new content is written. `json.dump` then streams JSON in chunks (Python's `json` module writes incrementally for `indent` mode). If the process is killed between the `open(... 'w')` and the end of `json.dump` — Windows shutdown, power loss, AV quarantine, segfault from a C extension (Qt/pynput/pystray are all native), the user closing the laptop lid during a write, or the daemon-thread OUI worker (line 1648) being terminated mid-call to `save_settings` at line 1628 when the main thread exits — the user is left with an **empty or truncated `settings.json`**. On next launch, `load_settings`'s `json.JSONDecodeError`-via-`except Exception` (line 1578) catches the parse failure and returns `DEFAULT_SETTINGS.copy()`, silently wiping the user's hotkey, format index, notification duration, OUI cadence, and `oui_last_downloaded` timestamp.
- **Why it's a bug:** F7 documented atomicity at the call-site level (multiple threads calling `save_settings` without a lock); F23 is the function-level confirmation that even a *single* writer is unsafe. The fix is the standard temp-file-plus-`os.replace` pattern that `oui_lookup.py` *attempted* (F2): write to `settings.json.tmp`, then `os.replace(tmp, settings.json)`. On Windows, `os.replace` is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` — a single syscall that atomically swaps the destination, so a reader/writer mid-rename sees either the old file or the new file but never a truncated one. The loss of `oui_last_downloaded` is the highest-impact knock-on: a wiped timestamp re-marks the OUI database as stale (per `OUIDatabase.is_stale`), causing an unwanted 3.5 MB IEEE download on next launch. Loss of `last_format_index` is mildly annoying. Loss of `hotkey` reverts to `alt+shift+m` which collides with whatever the user customized away from.
- **Proposed fix:**
  ```python
  def save_settings(settings):
      os.makedirs(SETTINGS_DIR, exist_ok=True)
      tmp_path = SETTINGS_PATH + '.tmp'
      with open(tmp_path, 'w', encoding='utf-8') as f:
          json.dump(settings, f, indent=2)
          f.flush()
          os.fsync(f.fileno())  # force kernel buffer to disk before rename
      os.replace(tmp_path, SETTINGS_PATH)
  ```
  Add a `threading.Lock()` at module scope (closes F7) and acquire it around the body so concurrent callers serialize. Consider catching `OSError` and re-raising with context for caller visibility, but do not swallow.
- **Effort:** S

### F26 [MEDIUM] OUI download worker is `daemon=True` — process exit during an in-flight `os.replace` corrupts the OUI database (links F2)

- **File:** `clipboard_hotkey.py:1648` (`oui_init_worker`), `clipboard_hotkey.py:730` (`OUIDownloadDialog` worker)
- **What:** Both OUI worker threads (the auto-update one started in `main()` at line 1648, and the manual one in `OUIDownloadDialog` at line 730) are `daemon=True`. Python's documented daemon-thread behavior is that the interpreter exits without waiting for them — they are **terminated abruptly** at the C runtime level (no Python-level cleanup, no `finally` blocks honored). If the user clicks Tray → Quit (`on_quit` at line 68-82) while either worker is mid-execution of `oui_lookup.OUIDatabase.download` and specifically inside the F2 window between `os.remove(self.oui_path)` (oui_lookup.py:102) and `os.rename(temp_path, self.oui_path)` (oui_lookup.py:103), the process dies with **no `oui.csv` on disk and an orphaned `oui.csv.tmp`**. On next launch, `OUIDatabase.is_stale` returns True (no file → stale), the auto-update worker fires, downloads again — but the orphaned `.tmp` is overwritten on the next `download()` call (line 79: `open(temp_path, 'wb')` truncates), so the leak is bounded to one orphan, not unbounded. F2 already covered the `os.rename`-failure case; F26 is the *process-termination* case during the same window, reaching the same corruption via a different trigger. F23's `save_settings` non-atomic write has the same hazard for `settings.json` — termination mid-`json.dump` leaves a zero-byte settings file (filed under F23 directly).
- **Why it's a bug:** `on_quit` (line 68) does:
  ```python
  icon.stop()
  if listener:
      listener.stop()
  exit_event.set()
  app = QApplication.instance()
  if app:
      app.quit()
  ```
  It does **not** call `oui_thread.join(timeout=...)`, does **not** signal the worker to abort cleanly, does **not** wait for an in-flight rename to complete. The Qt event loop returns from `app.exec_()` at line 1742, the `listener.stop()` at line 1744 runs, the interpreter then exits — and Python's daemon-thread termination is non-deterministic. On Windows, this is implemented via `TerminateThread` semantics (the OS unmaps the stack); any held kernel file handles are closed by the OS, but the *file system state* (`os.remove` already happened, `os.rename` not yet started) is permanent.
- **Proposed fix:** Track the OUI worker thread at module scope, change the quit path to:
  ```python
  def on_quit(icon, item):
      global listener, oui_thread
      icon.stop()
      if listener:
          listener.stop()
      exit_event.set()
      if oui_thread and oui_thread.is_alive():
          # Give the worker up to 3 seconds to finish an in-flight rename;
          # the network read is interruptible via a cooperative shutdown flag.
          oui_thread.join(timeout=3.0)
      app = QApplication.instance()
      if app:
          app.quit()
  ```
  Pair with a `_oui_shutdown_event = threading.Event()` checked inside `OUIDatabase.download`'s chunked read loop (oui_lookup.py:82) so the worker breaks out of the network read promptly; only the final rename block (~milliseconds) is the critical section that must complete. Combined with F2's fix (`os.replace` single-syscall), the corruption window collapses to a single atomic syscall that the OS will complete even on `TerminateThread`. F26 is filed separately from F2 because the fix is at the *call-site lifecycle* (clipboard_hotkey.py) rather than at the *atomic write* (oui_lookup.py) — both layers need to change.
- **Effort:** M

The Settings dialog writes via the seven-key explicit overwrite list (per F16 inspection at line 1030-1036) which **does not include `oui_last_downloaded`** — so the worker's timestamp write is preserved in memory by the dialog, but the **disk write race** means: worker truncates `settings.json`, partial JSON on disk; dialog also opens `settings.json` 'w' mode, truncates, writes its dict; result is whichever finished last. If the worker writes a dict with the new timestamp and the dialog writes a dict without it (because the dialog's read happened *before* the worker's mutation), the timestamp is lost.
- **Why it's a bug:** F7 documented the missing lock on `save_settings`; F28 names the **second concrete producer** (the OUI worker) reaching that race surface, separate from F16's same-process Qt-thread re-entrance. The user-visible symptom is: a successful OUI download writes `oui_last_downloaded`, the user immediately opens Settings, clicks Save (without changing anything), and the timestamp is overwritten with the prior (or null) value — causing the OUI database to be re-flagged stale and re-downloaded on next launch. Low severity individually (one extra 3.5 MB download), but it's the exact scenario the F7 fix (a `threading.Lock`) would also resolve.
- **Proposed fix:** Implementing F7 (module-level `_settings_lock = threading.Lock()` held around the entire body of `save_settings`) plus F23 (atomic temp-file + `os.replace`) closes this. Additionally, the OUI worker should `with _settings_lock: settings['oui_last_downloaded'] = ...; save_settings(settings)` to serialize the read-modify-write of the in-memory dict, not just the disk write. F28 is filed as Low rather than Medium because the disk-write race is already covered by F7/F23 and the in-memory mutation collision is itself benign (the dialog doesn't *read* `oui_last_downloaded`).
- **Effort:** S

### F29 [LOW] `listener.stop()` is called at end of `app.exec_()` only if `exit_event` was reached through `on_quit` — but `app.exec_()` can also return on other paths, leaving the pynput listener thread running until process exit

- **File:** `clipboard_hotkey.py:1742-1744`
- **What:** At line 1742, `app.exec_()` blocks until the Qt event loop is terminated. The standard exit path is `on_quit` → `app.quit()` → `app.exec_()` returns. But `app.exec_()` can also return on: (a) a Qt-internal fatal error, (b) the last window closing if `setQuitOnLastWindowClosed(True)` (currently False at line 1595, but a future refactor could change that), (c) `QApplication.quit()` called from anywhere (e.g. a future Settings dialog "Apply and Restart" button), (d) an unhandled C++ exception from a Qt slot bubbling out (rare but possible with PyQt5 native callbacks). On any of those paths, **the pynput listener thread is not stopped** until line 1744 executes — which it will, unconditionally, after `app.exec_()` returns. So actually F29 is **almost** a non-finding: the `if listener: listener.stop()` at line 1744 runs on every exit path. However: `listener.stop()` is asynchronous (per F27); the function returns immediately and the pynput thread shuts down on its own timeline. If `main()` returns before pynput's thread has cleaned up its Win32 hook (`UnhookWindowsHookEx`), the hook **leaks** for the process's remaining lifetime — which is short (the process exits microseconds later) but on Windows a leaked low-level keyboard hook can briefly continue to receive events targeted at the now-dying process, which the OS then has to clean up via the hook timeout (default 5 seconds before Windows force-removes a non-responsive low-level hook). For a user who restarts the app immediately after quit, the old hook from the dying process may still be partially registered when the new process tries to install its own hook, producing transient "listener not registered" or duplicate-fire behavior for ~5 seconds.
- **Why it's a bug:** Low severity, narrow window. The right pattern is `listener.stop(); listener.join(timeout=1.0)` so the call site blocks until pynput has actually removed its hook. Documenting as a finding because the task spec explicitly asked about listener lifecycle on quit. Note that pynput's `Listener` extends `threading.Thread` so `.join` is the standard primitive.
- **Proposed fix:**
  ```python
  app.exec_()
  if listener:
      listener.stop()
      try:
          listener.join(timeout=1.0)
      except RuntimeError:
          pass  # listener was never started (defensive)
  ```
  Combine with F26's OUI worker join and F27's QTimer stops to make `on_quit` deterministic.
- **Effort:** S

### F30 [LOW] OUI auto-update runs unconditionally at launch regardless of Qt event loop readiness — startup race between Qt event loop and OUI download progress puts queue lag

- **File:** `clipboard_hotkey.py:1610-1649`
- **What:** When `settings['oui_enabled']` is True (default), `main()` constructs the `OUIDatabase` (line 1611) and starts a daemon thread `oui_init_worker` (line 1648-1649) **before** entering `app.exec_()` (line 1742). The constructor sets up paths and reads `is_stale` (a stat call on `oui.csv` and a JSON load of `metadata.json`) — these are sub-millisecond on a warm cache, low-millisecond on a cold cache. The constructor does *not* download or load the full CSV (those happen inside the worker). So startup is not blocked. The "race" between Qt event loop start and hotkey listener thread start (line 1607: `listener = listen_hotkey(app)` runs *before* `app.exec_()`) is similarly benign: pynput's listener is on its own thread and dispatches independently of Qt; messages it produces (via `format_popup_request_queue.put`) are buffered until `poll_format_popup` runs under the Qt event loop. F30 is filed as Low because the race exists but produces only sub-second notification lag at startup; not a real bug.
- **Proposed fix:** None required; document for future refactors. If a perceived startup-lag complaint surfaces, a defensive `QTimer.singleShot(0, lambda: oui_thread.start())` would delay the OUI worker start until *after* the event loop is running, eliminating the lag at the cost of a tiny window where `is_stale` cannot be reported in the tray.
- **Effort:** S (deferred)

### F34 [LOW] PyInstaller `upx=True` triggers antivirus false positives on a fraction of Windows endpoints — distribution-friction risk for unsigned exe

- **File:** `mac-converter.spec:34`
- **What:** `upx=True` (line 34) enables UPX compression of the bundled exe and its embedded `.pyd`/DLL payload. UPX-compressed binaries match a heuristic signature used by Microsoft Defender, Avast, McAfee, ESET, and several other AV engines (per VirusTotal's public corpus of UPX-packed sample false-positive rates, typically 8-15% of engines flag UPX-packed Python exes). The exe is also **unsigned** (no `codesign_identity=...` — line 41 is `None`, and no Inno Setup `SignTool` directive in `installer.iss`). Combined: a fraction of users (estimated single-digit percent for Defender, higher for niche AVs) will see "MAC-Converter.exe was blocked" on first run. Not a code defect — the binary is benign — but a real distribution-friction issue.
- **Why it's a bug:** Severity Low because the app still runs once the user clicks through (or whitelists), and because UPX compression saves on download size (the unpacked exe is ~50-80MB with PyInstaller-bundled PyQt5/pynput/pystray/Pillow/pyperclip dependencies; UPX typically halves that). The trade-off is reasonable for a free utility. Documented here so the maintainer is aware: if user reports of "AV blocked the installer" surface, the first fix is `upx=False` in the spec; the second is buying a code-signing certificate (DigiCert/Sectigo, $150-400/year) and signing both the exe (via `signtool.exe` post-PyInstaller) and the installer (via Inno Setup's `SignTool=...` directive). Code-signing is the only durable fix because UPX or no, an unsigned binary will always trigger SmartScreen's "Unrecognized app" warning for the first N downloads until SmartScreen builds reputation.
- **Proposed fix:** Document only. No code change recommended unless user reports of AV blocking surface. If/when they do, the cheapest mitigation is `upx=False` (regenerates the exe without UPX compression; doubles download size but eliminates the UPX-heuristic FP class).
- **Effort:** N/A (documentation only)

### F36 [LOW] `env_load.ps1:9` renders literal `` `u001b[33m...`u001b[0m `` garbage instead of yellow text — broken developer-facing error message

- **File:** `env_load.ps1:9`

